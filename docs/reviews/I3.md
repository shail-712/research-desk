## Findings
1. **SHOULD — `aws_lambda/notify.py:53-56` with the live stream mapping: a `fail_delivery` replay can drop real
   alerts that land in the same stream batch.**
   - Notify stops at the first failed record and reports it, so Lambda retries from that record.
   - The live mapping uses batch 10, 3 retries, bisect off. Under Lambda's stream behaviour, when retries run out
     the batch from the failed record to its end is sent to the DLQ as metadata only, and the shard moves on.
   - So a real alert written within the same poll as the demo item would never be sent. It would stay
     `notified False` and appear only as one DLQ entry. Records behind it on the shard also wait for the
     retries (about 1 s here).
   - It didn't happen in I3: the demo ran at 17:55:43, and the real alerts came at 18:00.
   - PROGRESS says "the other alerts kept being delivered during the test". That's true of this run, but not
     guaranteed.
   - The same applies to a real Telegram failure, by design. A DLQ entry can stand for up to 10 alerts, and
     resending them is manual.
   - Fix:
     - Make the scan handler reject `fail_delivery` during the New York session (`in_session()`), with a unit
       test.
     - Add a DESIGN known-limitation line on what a DLQ entry means and how to resend FEED items that are
       `notified False`.
     - Optional: have Notify send `fail_delivery` items straight to the DLQ (it already has `sqs:SendMessage`)
       instead of failing the record.
   - I didn't reproduce this on AWS (that would mean writing to the stack). It's based on the documented stream
     semantics and on `test_notify_stops_at_the_first_failure_for_a_clean_retry`.
2. **SHOULD — `template.yaml:113-123` (`&ssmRead`, used at `:147`, `:162`, `:188`): every function can read
   every secret under `/research-desk`.**
   - Scan can read `TELEGRAM_BOT_TOKEN` and `APP_ACCESS_CODE`, and it needs neither.
   - Notify can read `GEMINI_API_KEY`, `FINNHUB_API_KEY` and `APP_ACCESS_CODE`, and it needs none of them.
   - Fix (I4 or a production note in DESIGN): give each function its own list of parameter ARNs
     (`ssm:GetParameters`), and have `aws_lambda/runtime.py` load only the names in a per-function env var.
3. **NICE — `template.yaml:161` (Scan's `DynamoDBCrudPolicy`): the live role also allows `DeleteItem`, `Scan`,
   `BatchWriteItem`, `BatchGetItem` and `index/*`.**
   - The scan path uses only Query (watchlist), GetItem (`has_event`), and PutItem plus ConditionCheckItem (the
     dedupe transaction).
   - Fix: replace it with an explicit statement listing those actions on `Table.Arn`, and check it with the
     moto tests.
4. **NICE — Notify's role: SAM attaches `AWSLambdaDynamoDBExecutionRole`, which allows stream reads
   (`GetRecords`, `GetShardIterator`, `DescribeStream`, `ListStreams`) on `Resource: "*"`.**
   - That covers every stream in the account.
   - Fix: an explicit statement on `!GetAtt Table.StreamArn` (keep `ListStreams` on `*`). Low impact today,
     since it's the only table.
5. **NICE — `docs/example_demo.md:91`, `:307`, `:328`: written before I3, so they say "`events: []`, empty until
   the Watchdog is deployed" and list the Watchdog as not done.**
   - The live feed now has 5 items.
   - The Postman demo request "B6 Alert feed (empty until I3)" only checks that `events` is an array, so it
     still passes, but its name is out of date.
   - Fix: update the expected result, add an I3 section (replay, `/feed`, DLQ and alarm, run outside market
     hours per finding 1), and rename B6.
6. **NICE — `docs/PROGRESS.md` (I3, DLQ bullet): the alarm times don't match the alarm history.**
   - PROGRESS gives ALARM at 17:59:23 and OK at 18:03:09 UTC.
   - The history has 17:58:58 and 18:02:58.
   - The order of events is right (purge at 17:59:44 came after ALARM). Fix: use the history timestamps.
7. **NIT — the deployed stream filter pattern contains a line break**
   (`…{"pk":\n{"S": ["FEED"]}}}}`).
   - `sam build` re-wrapped the long single-quoted string. It's still valid JSON and it works: the replay
     reached Notify.
   - Fix (optional): build the filter as a YAML mapping with `!Sub`/`Fn::ToJsonString`, or keep the string
     under the wrap width.
8. **NIT — local AWS CLI: the default region is `ap-south-1`.** That region is blocked by D17's SCP, so any
   command without `--region ap-southeast-2` fails or looks at the wrong place. It's not in git. Fix:
   `aws configure set region ap-southeast-2`.
